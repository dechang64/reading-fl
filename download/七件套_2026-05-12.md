### 三组对比

**对比一：融资速度 vs 盈利能力**

Figure AI，估值390亿美元。收入呢？数百万美元。

估值是收入的几千倍。这不是个案——整个具身智能赛道都面临同一个问题：钱来得太快，商业模式还没跑通。

2025年全年融资380亿，2026年一个季度就200亿。如果按这个速度，今年全年可能突破800亿。

但有多少企业能活到2027年？

**对比二：技术突破 vs 隐私风险**

具身智能的核心是"机器人+AI"。机器人需要感知环境、理解指令、执行动作。这意味着它需要大量的数据——你的家庭布局、你的生活习惯、你的语音特征、你的面部表情。

这些数据，比任何App收集的数据都敏感。

一个扫地机器人知道你家每个房间的布局。一个陪伴机器人知道你每天几点睡觉、跟谁说话、情绪什么时候低落。一个服务机器人知道你买什么、吃什么、去哪里。

当这些数据被上传到云端进行模型训练时，隐私风险是指数级的。

**对比三：开源热情 vs 安全审计**

2026奇点智能大会首次开源了AI原生联邦学习全栈系统（AN-FLS）。CVPR 2026录用了多模态联邦学习论文FedAFD。

开源是好事。但开源系统的安全审计跟上了吗？

上周OpenClaw曝出9个CVE，提醒我们：AI工具链的供应链安全是一个被严重低估的问题。具身智能的开源系统，一旦存在漏洞，影响的不只是数据，还有物理世界的安全。

### 联邦学习：具身智能的隐私底座

作为一个联邦学习研究者，我一直在思考一个问题：具身智能的隐私问题，怎么解？

传统方案是"数据上传到云端，在云端训练模型"。这对具身智能来说不可接受——你不会希望你家机器人的摄像头数据被上传到某个服务器上。

联邦学习提供了一条不同的路径：**数据不动，模型动。**

每个机器人/设备在本地训练模型，只把模型参数（梯度）上传到服务器进行聚合。原始数据永远不离开设备。

我在embodied-fl项目中的实践验证了这个思路：多模态联邦学习（视觉+语言+动作），FedAvg聚合，本地训练+全局聚合。数据留在本地，模型在联邦中进化。

但具身智能场景对联邦学习提出了新的挑战：

**1. 异构性更强**

不同品牌的机器人，传感器不同、算力不同、数据分布不同。一个扫地机器人和一个陪伴机器人的数据结构完全不同。传统的FedAvg在这种场景下效果会大打折扣。

**2. 通信成本更高**

具身智能的模型通常很大（多模态模型），每次上传的梯度参数量远超传统联邦学习场景。在带宽受限的物联网环境中，这是一个实际问题。

**3. 实时性要求**

机器人需要实时响应。联邦学习的聚合周期如果太长，模型更新跟不上环境变化。CVPR 2026的FedAFD论文提出的"统一对齐与蒸馏框架"，部分解决了这个问题——通过对齐不同客户端的表示空间，减少聚合轮次。

### OPC创业者的机会

如果你是一个OPC创业者，具身智能的融资狂欢意味着什么？

**不是让你去做机器人。**

做机器人需要硬件能力、供应链管理、大规模资金——这不是OPC的赛道。

OPC的机会在"具身智能的周边生态"：

**1. 隐私合规工具**

具身智能企业需要隐私合规方案。联邦学习即服务（FLaaS）、差分隐私工具、数据脱敏SDK——这些都是一个人+AI工具就能做的产品。

**2. 多模态数据处理**

具身智能产生海量多模态数据（视频、音频、传感器）。数据标注、质量评估、异常检测——这些是OPC可以切入的技术服务。

**3. 安全审计**

具身智能系统的安全审计（软件+硬件+通信）是一个新兴需求。上周OpenClaw的9个CVE已经敲响了警钟。一个人+AI工具+一套审计框架，就是一个安全审计服务。

**4. 内容和培训**

具身智能行业需要大量技术内容——论文解读、技术教程、行业分析。这正是OPC创作者的强项。

与此同时，Figure AI的估值达到390亿美元，但年收入仅数百万美元。

作为一个联邦学习研究者，同时维护着embodied-fl（具身智能联邦学习）等多个开源项目，我想从技术和商业两个角度聊聊这个问题。

### 一、为什么钱涌向具身智能？

三个原因：

**1. 技术拐点已到**

大语言模型（LLM）的突破让机器人有了"理解能力"。以前机器人只能执行预设指令，现在它可以理解自然语言、推理任务、适应新环境。这是质变。

**2. 政策强力推动**

中国人工智能学会发布《具身智能白皮书2026版》，36氪报告显示2025年融资380亿+，上交大穆尧称2026为"数据规模化元年"。政策+资本双轮驱动。

**3. 应用场景明确**

工业制造、家庭服务、医疗陪护、仓储物流——具身智能的落地场景比纯软件AI更直观、更容易被市场接受。

---

### 二、Figure AI的估值悖论

Figure AI估值390亿美元，年收入数百万美元。估值/收入比超过1000倍。

对比一下：
- OpenAI估值约$1500亿，年收入约$40亿，比约37倍
- Tesla市值约$8000亿，年收入约$970亿，比约8倍
- Figure AI估值$390亿，年收入数百万，比超过1000倍

这意味着市场在为"未来的可能性"买单，而不是为"当前的业绩"买单。

这本身不是问题——早期科技公司普遍估值偏高。但问题是：**具身智能的商业化路径比软件AI更长。**

软件AI（如ChatGPT）只需要服务器和API就能变现。具身智能需要硬件制造、供应链管理、渠道铺设、售后服务——每一步都是成本黑洞。

---

### 三、被忽视的隐私问题

融资讨论中，几乎没有人提到一个关键问题：**隐私。**

具身智能设备收集的数据类型：

| 设备类型 | 收集数据 | 隐私敏感度 |
|---------|---------|-----------|
| 扫地机器人 | 家庭布局、房间结构 | ⭐⭐⭐⭐ |
| 陪伴机器人 | 语音、面部表情、作息习惯 | ⭐⭐⭐⭐⭐ |
| 服务机器人 | 消费记录、行为模式 | ⭐⭐⭐⭐⭐ |
| 工业机器人 | 生产流程、工艺参数 | ⭐⭐⭐⭐ |

这些数据一旦泄露，后果远超App数据泄露。你家机器人的摄像头数据被上传到云端——你能接受吗？

---

### 四、联邦学习的解决方案

联邦学习（Federated Learning）是目前最可行的隐私保护方案：

**核心原理**：数据留在本地设备，只上传模型参数（梯度）到服务器进行聚合。

**具身智能场景的优势**：
- 机器人本身有计算能力（边缘计算），可以在本地训练
- 数据天然分布式（每个机器人/家庭的数据独立）
- 不需要集中存储原始数据

**具身智能场景的挑战**：

**1. 异构性（Non-IID问题）**

不同机器人的数据分布差异巨大。一个工厂机器人的数据和一个家庭机器人的数据完全不同。传统的FedAvg在这种场景下效果会显著下降。

我在embodied-fl项目中的实践发现，EWA-Fed（熵加权聚合）可以有效缓解这个问题——让"确定的客户端多说话"，抑制从众效应。

**2. 通信效率**

多模态模型（视觉+语言+动作）的参数量远超传统模型。每次联邦聚合需要传输大量梯度数据。在物联网环境中，带宽和延迟是实际瓶颈。

CVPR 2026的FedAFD论文提出了"统一对齐与蒸馏框架"——通过对齐不同客户端的表示空间，减少需要传输的参数量。这是一个有前景的方向。

**3. 实时性**

机器人需要实时响应环境变化。联邦学习的聚合周期（通常需要多轮通信）可能与实时性要求冲突。

解决方案：本地模型持续更新 + 全局模型定期聚合。本地模型负责实时响应，全局模型负责长期优化。

---

### 五、AN-FLS：开源联邦学习全栈系统

2026奇点智能大会开源的AN-FLS（AI-Native Federated Learning System），是目前最完整的开源联邦学习系统。

它的意义在于：降低了联邦学习的工程门槛。以前你需要自己搭建通信框架、聚合服务器、客户端SDK。现在AN-FLS提供了全栈方案。

对OPC创业者来说，这意味着：
- 你不需要从零开始构建联邦学习基础设施
- 你可以基于AN-FLS开发垂直领域的隐私计算产品
- 一个人+AI工具+开源框架 = 可行的产品原型

### 六、我的判断

具身智能赛道：

- **短期（1-2年）**：融资继续火热，但会出现第一批倒闭潮。能活下来的企业，是那些同时解决技术和隐私问题的。

### 一、具身智能为什么需要联邦学习？

传统AI训练流程：

```
设备采集数据 → 数据上传云端 → 云端集中训练 → 模型下发设备
```

对具身智能来说，这个流程有三个致命问题：

1. **隐私泄露**：机器人采集的家庭/工业数据上传云端，一旦泄露后果严重
2. **带宽瓶颈**：多模态数据（视频+音频+传感器）体积巨大，上传成本高
3. **实时性差**：云端训练→下发的延迟，无法满足机器人实时响应需求

联邦学习方案：

```
设备本地训练 → 只上传模型梯度 → 服务器聚合 → 更新后的模型下发
```

原始数据永远不离开设备。传输的是模型参数，不是原始数据。

**Layer 1: Python ML核心**

```python
# fl_engine.py - 联邦聚合引擎
import torch
from typing import List, Optional

def ewa_fed_aggregate(
    params_list: List[torch.Tensor],
    client_data_sizes: Optional[List[int]] = None,
    entropy_weights: Optional[torch.Tensor] = None
) -> torch.Tensor:
    """
    EWA-Fed: 熵加权联邦聚合
    
    解决具身智能场景的Non-IID问题：
    - 不同机器人的数据分布差异大
    - 简单平均（FedAvg）效果差
    - 熵加权让"确定的客户端多说话"
    
    参数:
        params_list: 各客户端的模型参数
        client_data_sizes: 各客户端的数据量（用于样本数加权）
        entropy_weights: 各客户端的熵权重（用于EWA加权）
    
    返回:
        聚合后的全局模型参数
    """
    if client_data_sizes is None:
        # 向后兼容：无数据量信息时退化为等权平均
        return torch.mean(torch.stack(params_list), dim=0)
    
    total = sum(client_data_sizes)
    weights = torch.tensor([n / total for n in client_data_sizes])
    
    if entropy_weights is not None:
        # EWA加权：样本数权重 × 熵权重
        weights = weights * entropy_weights
        weights = weights / weights.sum()  # 重新归一化
    
    return sum(w * p for w, p in zip(weights, params_list))


def compute_entropy_weights(
    client_losses: List[float],
    temperature: float = 1.0
) -> torch.Tensor:
    """
    计算熵权重
    
    核心思想：损失越低（模型越确定）的客户端，权重越高
    这避免了"不确定的客户端带偏全局模型"的问题
    
    参数:
        client_losses: 各客户端的本地训练损失
        temperature: 温度参数，控制权重分布的平滑程度
    
    返回:
        归一化的熵权重
    """
    # 将损失转化为"确定性分数"（损失越低越确定）
    certainty = 1.0 / (torch.tensor(client_losses) + 1e-8)
    
    # 温度缩放
    scaled = certainty / temperature
    
    # Softmax归一化
    weights = torch.softmax(scaled, dim=0)
    
    return weights
```

**Layer 2: 客户端训练**

```python
# client.py - 具身智能客户端
import torch
import torch.nn as nn
from models.vision import VisionEncoder
from models.language import LanguageEncoder
from models.action import ActionDecoder

class EmbodiedClient:
    """具身智能联邦学习客户端"""
    
    def __init__(self, client_id: str, device: str = "cpu"):
        self.client_id = client_id
        self.device = device
        
        # 多模态模型
        self.vision_encoder = VisionEncoder().to(device)
        self.language_encoder = LanguageEncoder().to(device)
        self.action_decoder = ActionDecoder().to(device)
        
        # 本地数据（不离开设备！）
        self.local_data = None
    
    def load_local_data(self, data):
        """加载本地数据（隐私关键：数据不离开此设备）"""
        self.local_data = data
    
    def local_train(self, global_params: dict, epochs: int = 5) -> dict:
        """
        本地训练
        
        1. 用全局参数初始化本地模型
        2. 在本地数据上训练
        3. 返回更新后的参数（梯度），不返回数据
        """
        # 加载全局参数
        self._load_params(global_params)
        
        # 本地训练
        optimizer = torch.optim.Adam(self._get_params(), lr=1e-4)
        
        for epoch in range(epochs):
            total_loss = 0
            for batch in self.local_data:
                # 多模态输入：图像 + 语言指令 + 动作标签
                images, instructions, actions = batch
                
                # 前向传播
                visual_feat = self.vision_encoder(images)
                lang_feat = self.language_encoder(instructions)
                fused = visual_feat + lang_feat  # 简化融合
                pred_actions = self.action_decoder(fused)
                
                # 计算损失
                loss = nn.MSELoss()(pred_actions, actions)
                
                # 反向传播
                optimizer.zero_grad()
                loss.backward()
                optimizer.step()
                
                total_loss += loss.item()
            
            avg_loss = total_loss / len(self.local_data)
        
        # 返回模型参数（不是数据！）
        return {
            "client_id": self.client_id,
            "params": self._get_params_dict(),
            "data_size": len(self.local_data),
            "avg_loss": avg_loss
        }
    
    def _load_params(self, params: dict):
        """加载全局参数到本地模型"""
        self.vision_encoder.load_state_dict(params["vision"])
        self.language_encoder.load_state_dict(params["language"])
        self.action_decoder.load_state_dict(params["action"])
    
    def _get_params_dict(self) -> dict:
        """获取本地模型参数"""
        return {
            "vision": self.vision_encoder.state_dict(),
            "language": self.language_encoder.state_dict(),
            "action": self.action_decoder.state_dict()
        }
```

### 三、FedAFD的核心思想

CVPR 2026录用的FedAFD论文提出了"统一对齐与蒸馏框架"，核心解决两个问题：

**问题1：表示空间不对齐**

不同客户端的多模态特征分布不同（Non-IID）。直接聚合会导致"特征冲突"。

**解决方案**：在聚合前，先对齐各客户端的表示空间。

```python
def align_representations(
    client_features: List[torch.Tensor],
    target_distribution: torch.Tensor
) -> List[torch.Tensor]:
    """
    对齐各客户端的特征表示到目标分布
    
    FedAFD的核心思想：
    在聚合前先对齐，减少特征冲突
    """
    aligned = []
    for feat in client_features:
        # 计算当前分布与目标分布的差异
        mean_diff = target_distribution.mean(dim=0) - feat.mean(dim=0)
        std_ratio = target_distribution.std(dim=0) / (feat.std(dim=0) + 1e-8)
        
        # 对齐：平移 + 缩放
        aligned_feat = (feat - feat.mean(dim=0)) * std_ratio + target_distribution.mean(dim=0)
        aligned.append(aligned_feat)
    
    return aligned
```

**问题2：通信成本高**

多模态模型参数量大，每次聚合传输成本高。

**解决方案**：知识蒸馏——用一个小模型（学生）学习大模型（教师）的知识，只传输学生模型的参数。

```python
def distill_model(
    teacher_params: dict,
    student_model: nn.Module,
    data_loader,
    temperature: float = 3.0
) -> dict:
    """
    知识蒸馏：大模型→小模型
    
    在联邦学习中：
    - 各客户端训练大模型（教师）
    - 聚合后蒸馏到小模型（学生）
    - 只传输学生模型参数（大幅减少通信成本）
    """
    student_model.train()
    optimizer = torch.optim.Adam(student_model.parameters(), lr=1e-3)
    
    for batch in data_loader:
        inputs, _ = batch
        
        # 教师模型的软标签
        with torch.no_grad():
            teacher_output = teacher_forward(teacher_params, inputs)
            soft_labels = torch.softmax(teacher_output / temperature, dim=1)
        
        # 学生模型输出
        student_output = student_model(inputs)
        student_log_softmax = torch.log_softmax(student_output / temperature, dim=1)
        
        # 蒸馏损失
        distill_loss = nn.KLDivLoss(reduction="batchmean")(
            student_log_softmax, soft_labels
        ) * (temperature ** 2)
        
        optimizer.zero_grad()
        distill_loss.backward()
        optimizer.step()
    
    return student_model.state_dict()
```

### 隐私协议

我后来仔细看了那个陪伴机器人的隐私协议。

说实话，写得挺专业的。用了大量法律术语，什么"匿名化处理"、"数据加密传输"、"最小必要原则"。

但问题是：

**"匿名化处理"的视频，真的匿名吗？**

如果你家客厅的布局是独一无二的，那这段视频即使模糊处理了人脸，仍然可以识别出是你家。

**"数据加密传输"的数据，到了服务器上还加密吗？**

传输过程加密了，但到了服务器上，公司的人是可以解密查看的。数据标注员（比如我）每天就在看这些"加密"过的数据。

**"最小必要原则"收集的数据，真的"最小"吗？**

机器人需要知道你几点起床才能在合适的时间叫你吗？需要知道你跟谁说话说了多久才能推荐音乐吗？

这些问题的答案，取决于你怎么定义"必要"。

### 联邦学习

实习第三个月，公司请了一个外部顾问来做技术分享。

那个顾问讲了一个东西，叫"联邦学习"。

他说，现在的做法是"数据上传到云端，在云端训练模型"。这就像把你的日记本寄给一个陌生人，让他帮你总结你最近的心情。

联邦学习的做法是：日记本留在你手里，你自己在家里总结心情，然后把"总结"（不是日记内容）寄过去。

"总结"就是模型参数。它包含了模型学到的"知识"，但不包含任何原始数据。

我当时觉得这个思路很聪明。但我也问了一个问题："那公司怎么用这些数据做模型训练呢？"

顾问说："不需要原始数据。各设备在本地训练模型，然后把模型参数上传聚合。聚合后的全局模型再下发给各设备。原始数据永远不离开设备。"

老张在旁边听了一会儿，说："道理我都懂，但工程上能做到吗？"

顾问说："现在可以了。CVPR 2026刚录用了FedAFD论文，专门解决多模态联邦学习的问题。奇点大会也开源了AN-FLS全栈系统。工具链已经成熟了。"

---

### 为什么还没用

我问老张："那公司为什么不用联邦学习？"

老张想了想，说了三个原因：

**第一，成本。**

现有的架构已经搭好了，换成联邦学习需要重写大量代码。三十个人的公司，没有精力做这种架构级别的改动。

**第二，效果。**

集中式训练的效果通常比联邦学习好。因为集中式训练能看到所有数据，联邦学习只能看到聚合后的参数。对于公司来说，模型效果直接关系到产品竞争力。

**第三，用户不关心。**

"你觉得用户在乎隐私吗？"老张问我。

我说："应该在乎吧。"

老张说："你去看看我们的用户反馈，有几个人提过隐私问题？"

他打开用户反馈系统，搜了一下"隐私"。

结果：两百多条反馈中，提到"隐私"的只有三条。其中两条是问"机器人会不会偷拍"，一条是问"数据存在哪里"。

"三条，"老张说，"两百条反馈里只有三条。你觉得公司会为了三条反馈去重写架构吗？"

---

### 但事情在变

实习结束的时候，有两件事让我觉得情况可能会变。

**第一件事**：最高法开始起草AI生成作品著作权归属文件。虽然不是直接针对隐私，但释放了一个信号——AI相关的法律框架正在加速完善。

**第二件事**：欧盟的AI Act开始执行，对高风险AI系统（包括家用机器人）的隐私保护提出了明确要求。如果公司的产品要出口欧洲，就必须满足这些要求。

老张说："国内可能也会跟进。只是时间问题。"

---

### 我学到的

三个月实习，我学到的最重要的一件事不是技术，是一个判断：

**隐私问题不是"会不会爆发"的问题，是"什么时候爆发"的问题。**

具身智能收集的数据，比任何App都敏感。当第一起大规模隐私泄露事件发生时（不是"如果"，是"当"），整个行业会被强制要求改变。

到那个时候，联邦学习就不是"可选方案"了，而是"必选方案"。

提前布局联邦学习的企业，会在那一天到来时占据优势。

还在用"用户不关心"当借口的企业，会在那一天到来时措手不及。

---

### 写在最后

如果你问我，具身智能赛道值不值得关注？

值得。200亿的融资不是假的，技术突破是真的，应用场景是明确的。

但如果你要入局，我建议你关注两个方向：

**第一，隐私计算。** 联邦学习、差分隐私、安全多方计算——这些技术在未来会成为具身智能的标配。现在学，就是提前占位。

**第二，安全审计。** 上周OpenClaw曝出9个CVE，提醒我们AI工具链的安全问题不容忽视。具身智能系统一旦有漏洞，影响的不只是数据，还有物理安全。

这两个方向，都是一个人+AI工具就能做的。

不需要大团队，不需要大资金。

只需要你愿意在这个领域深耕。
