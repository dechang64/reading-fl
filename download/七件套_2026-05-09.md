## 一、公众号 | SOHOForce OPC AI开放创造实验室

### 标题
**AI是让阅读变浅了，还是变深了？一个实验者的回答**

### 发布时间
**2026-05-09 10:00**（周六上午，公众号阅读高峰 9:30-11:00）

### 正文

上周有一个学生在课后问我：老师，你觉得AI会让阅读变浅吗？

他说，以前读一本书要一周，现在让AI总结一下，五分钟就"读完了"。以前写读书笔记要两小时，现在让AI生成一下，十秒钟就"写完了"。

他说完之后，教室里安静了几秒钟。因为所有人都知道他说的是事实。

---

### AI的"效率陷阱"

AI确实让信息获取变快了。这是事实，不需要否认。

但"获取信息"和"阅读"是两件事。

你用AI总结一本书，得到的是信息的骨架——主题、结构、关键论点。但阅读的肉——那些让你停下来反复读的句子、那些让你在深夜流泪的段落、那些你不知道为什么被打动但就是被打动了的瞬间——AI给不了你。

上周另一个学生说了一句让我印象深刻的话。她说，我用AI总结了一本书，然后去看了原文。我发现AI漏掉了我最喜欢的那一段。

我问她，哪一段？

她说，就是那种……你读完之后会发呆很久的那一段。AI觉得那段不重要，因为那段对论证主题没有贡献。但对我来说，那段是整本书的灵魂。

---

### Reading-FL：读懂沉默

这让我想到我们实验室在做的一个项目——Reading-FL。

Reading-FL是一个联邦阅读情感模型。简单说，它做的事情是：分析你在阅读时的情感反应——你在哪些段落停留了、停留了多久、标注了什么感受——然后用这些数据训练一个模型，帮你找到"情绪邻居"。

什么是"情绪邻居"？就是那些在不同地方、读不同书、但和你有相似情感体验的人。

三个校区，273条书摘，数据全部留在各校区本地，用联邦学习聚合。准确率85.5%。

但我想说的不是准确率。我想说的是这个项目揭示的一个事实：

**阅读中最有价值的数据，不是"你读了什么"，而是"你在哪里停了下来"。**

AI总结工具关注的是"你读了什么"——它提取信息、压缩内容、输出摘要。但Reading-FL关注的是"你在哪里停了下来"——它捕捉沉默、记录停顿、理解那些无法用语言表达的被打动。

这两种AI，指向完全不同的方向。

---

### 坐忘灯的"读懂沉默"

我们在做的坐忘灯，核心功能之一就是"读懂沉默"。

当你在灯下读书，灯不会帮你总结这本书讲了什么。灯做的是：记录你在哪些段落停了下来。

然后，灯会做两件事：

第一，它会在本地分析你的阅读模式——你偏好什么类型的书、什么风格的语言、什么样的情感节奏。这些数据永远不离开你的设备。

第二，它会通过联邦学习，在保护隐私的前提下，帮你找到那些和你有相似阅读情感的人。不是"读了同一本书"的人，而是"在同一类段落被打动"的人。

**区别很大。**

"读了同一本书"是表面匹配。你可能和一个人读了同一本《百年孤独》，但打动你的段落完全不同——你被打动的是马孔多的雨，他被打动的是最后的飓风。

"在同一类段落被打动"是深层匹配。你可能读的是《百年孤独》，他读的是《红楼梦》，但你们都在"描写孤独的段落"停了下来。这种匹配，比书名匹配有价值得多。

---

### 全民阅读的真正问题

每年全民阅读周，都会出现大量的"阅读推广"内容——推荐书单、打卡活动、阅读挑战。

这些活动有没有用？有用。它们让更多人开始读书。

但它们解决的是"量"的问题——你一年读了多少本书。

全民阅读的真正问题不是"量"，是"质"。不是"你读了多少"，是"你读得多深"。

AI可以帮你读得更多——五分钟总结一本书，一天"读"十本。但AI也可以帮你读得更深——分析你的阅读模式，找到你的情绪邻居，让你知道"原来也有人在这段话前停了下来"。

关键在于：你选择让AI做什么。

---

OPC（Open Platform Creator）不只是技术概念，它也是一种阅读观。

传统的阅读推广是"自上而下"的——专家推荐书单、平台推送内容、排行榜制造焦虑。

OPC的阅读是"自下而上"的——一个人，用AI工具，找到自己的阅读节奏、自己的情感共鸣、自己的阅读社区。

## 三、知乎 | 小蠹OPC

### 标题
**联邦学习在阅读推荐中到底有没有必要？来自Reading-FL实验的真实数据**

### 发布时间
**2026-05-09 15:00**（知乎下午技术阅读高峰 14:00-16:00）

### 正文

先说结论：**有必要，但不是因为大多数人以为的那个原因。**

大多数人认为联邦学习在阅读推荐中的价值是"隐私保护"——用户的阅读数据不应该离开设备。这个理由当然成立，但它不是最关键的原因。

最关键的原因是：**阅读数据天然是Non-IID的，集中式聚合会抹杀个性化。**

---

### 一、Reading-FL实验回顾

Reading-FL是我们实验室的一个联邦阅读情感模型项目。实验设置：

- 3个校区（西浦不同学院的学生）
- 273条书摘（学生在阅读时标注的段落+情感标签）
- 每个校区的数据留在本地，只上传模型梯度
- FedAvg聚合，准确率85.5%

这个实验验证了两件事：
1. 联邦学习可以在保护隐私的前提下完成阅读情感分类
2. 多个校区的协作训练比单个校区独立训练效果更好

但实验过程中发现了一些有趣的现象，值得展开讨论。

---

### 二、Non-IID：阅读数据的本质特征

传统推荐系统假设用户数据是独立同分布的（IID）。但阅读数据天然违反这个假设。

**校区A（计算机学院）**的学生倾向于标注技术类书籍的段落，情感标签以"启发""困惑""兴奋"为主。

**校区B（人文学院）**的学生倾向于标注文学类书籍的段落，情感标签以"感动""共鸣""忧伤"为主。

**校区C（商学院）**的学生倾向于标注商业/传记类书籍的段落，情感标签以"激励""反思""认同"为主。

如果用集中式方法把所有数据混在一起训练，模型会倾向于预测出现频率最高的情感标签（比如"认同"），而忽略低频但同样有价值的标签（比如"困惑"或"忧伤"）。

联邦学习的优势在于：每个校区先在本地训练一个个性化模型，然后只共享模型参数（梯度），不共享原始数据。聚合后的全局模型保留了各校区的"个性"，同时获得了"共性"的提升。

---

### 三、为什么集中式方法不够？

有人会问：为什么不直接在服务器上训练一个模型，然后给每个用户做个性化微调？

三个原因：

**1. 数据合规**

阅读数据包含个人偏好、情感反应、甚至心理状态。根据《个人信息保护法》，这类敏感数据需要用户明确同意才能收集和处理。集中式存储意味着平台拥有所有用户的阅读数据，一旦数据泄露，后果严重。

**2. 冷启动问题**

新用户没有历史数据，集中式模型无法为其提供个性化推荐。联邦学习可以通过"迁移学习"解决——用全局模型作为初始化，新用户只需少量本地数据就能获得不错的体验。

**3. 数据分布漂移**

用户的阅读偏好会随时间变化。集中式模型需要定期重新训练，成本高、延迟大。联邦学习支持增量更新——每个用户在本地持续训练，模型始终反映最新的阅读状态。

---

### 四、Reading-FL的三个技术挑战

说了优势，也要说挑战。

**挑战1：情感标签的粒度**

当前实验使用10个情感标签（感动、共鸣、忧伤、启发、困惑、兴奋、激励、反思、认同、平静）。但真实的阅读情感远比这复杂——"被一段话打动到说不出话"和"觉得这段话写得真好"是不同的情感，但可能都被标注为"感动"。

更细粒度的情感标签需要更多的标注数据，而标注数据本身就是一个瓶颈。

**挑战2：跨语言阅读**

西浦是中英双语教学环境。学生的阅读材料中，中文和英文的比例大约是6:4。当前模型只处理中文书摘，英文书摘被排除在外。

跨语言联邦阅读情感分析是一个开放问题——不同语言的"情感表达"方式不同，直接翻译会丢失情感信息。

**挑战3：评估指标**

准确率85.5%看起来不错，但"准确率"本身就是一个有问题的指标。在阅读情感分析中，"准确"不等于"有用"。一个模型可能准确预测了"这段话让人感动"，但如果它不能解释"为什么让人感动"，它的价值就有限。

我们正在探索"可解释性"指标——模型不仅要预测情感，还要给出预测理由（比如"这段话使用了第二人称，营造了亲密感"）。

---

### 五、twc-core：让联邦学习更简单

Reading-FL的底层依赖是我们开发的twc-core——一个共享的联邦学习Python包。

twc-core把联邦学习的常用模块打包在一起：特征提取、模型训练、FedAvg聚合、HNSW向量索引、审计链。56项核心测试全过，8个项目共344项测试全过。

为什么需要twc-core？因为联邦学习的"基础设施"重复率极高。每次开新项目，都在写同样的代码——FedAvg聚合逻辑、梯度压缩、客户端选择策略、审计日志。写到第八个项目的时候，我说不行了，得抽出来。

twc-core的目标是：让研究者把精力放在"问题定义"和"模型设计"上，而不是"基础设施搭建"上。

---

### 六、我的判断

联邦学习在阅读推荐中不是"锦上添花"，而是"雪中送炭"。

阅读数据的隐私敏感性、Non-IID分布特征、以及个性化需求，都指向同一个结论：**集中式方法在阅读场景下有结构性缺陷。**

联邦学习不是完美的解决方案（冷启动、标签粒度、跨语言、评估指标都是开放问题），但它是目前最接近"既保护隐私又提供个性化"的技术路径。

### 为什么要做 twc-core？

去年秋天，我在同时维护 6 个联邦学习项目。每个项目都独立实现了以下模块：

### 设计理念

twc-core 的设计遵循三个原则：

**原则一：接口先行**

每个模块先定义接口契约（Protocol/ABC），再分别实现。这避免了 analysis 层和 UI 层方法名不匹配的问题。

```python
from typing import Protocol

class Aggregator(Protocol):
    """联邦聚合器接口"""
    def aggregate(self, params_list: list, 
                  client_data_sizes: list = None) -> dict:
        """聚合多个客户端的模型参数"""
        ...
```

**原则二：向后兼容**

所有函数的签名都支持渐进式升级。比如 FedAvg 聚合：

```python
def fedavg_aggregate(params_list, client_data_sizes=None):
    if client_data_sizes is None:
        # 退化为等权平均（向后兼容）
        return {k: sum(p[k] for p in params_list) / len(params_list)
                for k in params_list[0]}
    else:
        # 按样本数加权（标准FedAvg）
        total = sum(client_data_sizes)
        return {k: sum(
            p[k] * s / total 
            for p, s in zip(params_list, client_data_sizes)
        ) for k in params_list[0]}
```

**原则三：测试驱动**

56 项核心测试覆盖所有模块。每个下游项目还有自己的测试（共 344 项）。修改 twc-core 时，所有 8 个项目的测试都要通过。

### 核心模块详解

**1. FedAvg 聚合（aggregation/fedavg.py）**

标准 FedAvg 公式：w_global = Σ(n_k/N) × w_k

```python
def fedavg_aggregate(params_list, client_data_sizes=None):
    """
    联邦平均聚合
    
    Args:
        params_list: 客户端模型参数列表
        client_data_sizes: 各客户端数据量（None时退化为等权）
    
    Returns:
        聚合后的全局模型参数
    """
    if not params_list:
        raise ValueError("params_list不能为空")
    
    if client_data_sizes is None:
        # 等权平均（向后兼容）
        n = len(params_list)
        return {
            k: sum(p[k] for p in params_list) / n
            for k in params_list[0]
        }
    
    if len(params_list) != len(client_data_sizes):
        raise ValueError(
            f"参数列表长度({len(params_list)})与"
            f"数据量列表长度({len(client_data_sizes)})不匹配"
        )
    
    # 按样本数加权（标准FedAvg）
    total = sum(client_data_sizes)
    if total == 0:
        raise ValueError("数据量总和不能为0")
    
    return {
        k: sum(
            p[k] * (s / total) 
            for p, s in zip(params_list, client_data_sizes)
        )
        for k in params_list[0]
    }
```

踩坑记录：最初实现时用了 `.mean(dim=0)` 做简单平均，没有按样本数加权。这在四个项目（defect-fl、embodied-fl、reading-fl、organoid-fl）中都犯了同样的错误。审计时才发现——**同一项目多实现盲区**：organoid-fl 有两个独立的 FedAvg 实现，修了一个漏了另一个。

教训：**审计不能只看函数名，要看所有调用路径和所有同名函数。**

**2. HNSW 向量索引（index/hnsw.py）**

HNSW（Hierarchical Navigable Small World）用于高维向量的近似最近邻搜索。在多个项目中用于相似度匹配：

- Embodied-FL：任务相似度匹配
- FundFL：基金风险画像相似度
- Reading-FL：阅读情感向量匹配

核心 API：

```python
from twc_core.index.hnsw import HNSWIndex

index = HNSWIndex(m=16, ef_construction=200, ef_search=50)

# 插入向量
index.insert("doc_001", [0.1, 0.2, 0.3, ...])
index.insert("doc_002", [0.4, 0.5, 0.6, ...])

# 搜索最近邻
results = index.search(query=[0.15, 0.25, 0.35, ...], k=5)
# 返回: [("doc_001", 0.98), ("doc_002", 0.85), ...]
```

# tests/test_core.py

def test_fedavg_weighted():
    """测试加权FedAvg"""
    params = [{"w": 1.0}, {"w": 3.0}]
    sizes = [100, 300]
    result = fedavg_aggregate(params, sizes)
    assert abs(result["w"] - 2.5) < 1e-6  # (1*100 + 3*300) / 400

def test_fedavg_equal_weights():
    """测试等权FedAvg（向后兼容）"""
    params = [{"w": 1.0}, {"w": 3.0}]
    result = fedavg_aggregate(params)
    assert abs(result["w"] - 2.0) < 1e-6  # (1+3) / 2

def test_fedavg_empty_params():
    """测试空参数列表"""
    with pytest.raises(ValueError):
