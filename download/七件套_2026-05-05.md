### 坐忘书房的立夏实验

立夏这天，我想聊聊一个正在进行中的实验。

坐忘书房和西浦融创书院联合打造了一个品牌沙龙，叫"创坐会"。核心命题很简单：**AI能不能让阅读变得更深，而不是更浅？**

微信读书让你读得更多。但"更多"不等于"更深"。

我们的方案是Reading-FL——一个联邦阅读情感模型。三个校区，273条书摘，数据全部留在本地，只上传模型梯度。FedAvg聚合后准确率85.5%。

为什么用联邦学习？因为阅读偏好是隐私。你读什么书、在哪个段落停留、标注了什么感受——这些数据不应该离开你的设备。

**Reading-FL证明了一件事：安静的社交是可能的。** 你不需要暴露自己的阅读品味，模型依然能帮你找到"情绪邻居"——那些在不同地方、读不同书、但和你有相似情感体验的人。

这就是坐忘灯的底层逻辑：**微信读书让你读得更多，坐忘灯让你读得更深。**

### 具身智能的"数据饥荒"

最近36氪发了一篇报道，标题很直白：**中国机器人4家头部公司面临"数据供给危机"。**

具身智能（Embodied AI）的瓶颈不在算法，在数据。

人形机器人需要海量的真实物理交互数据来训练——抓取、行走、避障、操作工具。这些数据无法像文本数据那样从互联网上大规模采集，必须通过实际物理交互获得。

这跟OPC面临的问题惊人地相似：**高质量的专业数据是稀缺资源，而且天然分散。**

联邦学习给出的解法是：数据不动，模型动。每个机器人（或每个OPC创作者）在本地训练，只共享模型更新。

EWA-Fed的实验进一步证明：不是所有数据贡献都等价。"确定的客户端多说话"——数据质量高的节点获得更高聚合权重。三组真实实验平均提升18个百分点。

**具身智能的数据饥荒，恰恰是联邦学习最大的机会窗口。**

一周之内，中国两个最前沿的城市同时向OPC创业者伸出了手。

---

### 一、双城竞跑的产业逻辑

深圳和上海的OPC布局有明显的差异化定位：

| 维度 | 深圳 | 上海 |
|------|------|------|
| 策略 | 政策驱动（行动计划） | 平台驱动（Skill Store） |
| 重点 | 创业生态（资金+培训+空间） | 技能交易（平台+加速器） |
| 优势 | 硬件供应链+创业文化 | 金融+国际化+人才密度 |
| 信号 | "政府帮你创业" | "市场帮你变现" |

深圳走的是"自上而下"路线——政府发文、政策配套、资源对接。
上海走的是"自下而上"路线——建平台、做交易、让市场说话。

两条路线并行，说明OPC已经过了"概念验证"阶段，进入了"基础设施竞赛"阶段。

---

### 二、Skill Store的隐含假设

上海浦东的"Skill Store"是一个技能交易平台。OPC创作者可以在上面发布、交易、组合自己的AI技能。

但这里有一个隐含假设：**技能可以脱离数据独立存在。**

实际上，大多数高价值技能都深度绑定数据：
- 一个擅长金融分析的AI技能，需要金融数据训练
- 一个擅长医学影像诊断的技能，需要医学数据训练
- 一个擅长阅读推荐的技能，需要用户行为数据训练

如果技能在平台上交易，数据在哪里？

方案A：数据集中到平台 → 隐私风险、数据垄断、创作者失去议价权
方案B：数据留在本地 → 需要联邦学习

**Skill Store要真正运转，联邦学习不是可选项，是必选项。**

---

### 三、联邦学习在OPC中的三个未解决问题

知乎用户更关心技术细节，这里不重复公众号的"三个角色"框架，而是聚焦**尚未解决的问题**。

**问题1：非IID数据下的OPC聚合**

传统联邦学习假设客户端数据是独立同分布的（IID）。但OPC场景下，每个创作者的数据分布天然不同——一个做金融分析的OPC和一个做阅读推荐的OPC，数据分布差异极大。

EWA-Fed用entropy加权部分解决了这个问题（三组实验平均+18pp），但entropy只衡量模型不确定性，不衡量数据分布差异。当两个客户端的模型都很"确定"但方向完全相反时，EWA-Fed会怎么处理？

这是开放问题。

**问题2：OPC的"信任冷启动"**

联邦学习需要多个客户端参与聚合才有意义。但OPC的定义就是"一个人"——一个人怎么联邦？

可能的路径：
- **跨OPC联邦**：多个OPC创作者共享模型能力，但各自保留数据。类似Skill Store的"联邦模式"
- **时间联邦**：同一个OPC创作者在不同时间段的数据作为不同客户端。今天的数据和昨天的数据联邦训练
- **人机联邦**：创作者的判断作为"ground truth"，AI模型作为"客户端"，两者联邦

第三种路径最有趣，但目前几乎没有研究。

**问题3：联邦学习的OPC工具链成熟度**

twc-core把联邦学习核心模块抽成了共享Python包（8个项目344项测试全过），但距离"OPC即插即用"还有距离：

- 缺少OPC场景的联邦学习框架（现有框架如Flower、FedML面向企业级部署，对单人开发者不友好）
- 缺少"联邦学习即服务"的SaaS产品（OPC创作者不应该自己搭建联邦学习基础设施）
- 缺少联邦学习的可视化Dashboard（EWA-Fed的Streamlit Dashboard是第一步，但还不够）

**这三个问题，每一个都是一个研究方向。**

### 关键技术决策

**1. 内存SQLite + 单例连接**

Streamlit Cloud文件系统只读，无法创建持久化 `.db` 文件。

```python
import sqlite3
import threading

DB_PATH = ":memory:"
_lock = threading.Lock()
_connection = None

def get_db():
    global _connection
    if _connection is None:
        _connection = sqlite3.connect(DB_PATH, check_same_thread=False)
        _connection.row_factory = sqlite3.Row
    return _connection
```

关键点：
- `:memory:` 数据库每次进程重启清空（Streamlit Cloud可接受，树洞内容是临时的）
- 线程锁防止并发写入冲突
- 单例连接确保内存数据库的表在所有模块间共享
- `init_db()` 在 `db.py` 模块末尾自动调用，`import db` 时表已建好

**2. MiniMax API（OpenAI兼容格式）**

```python
import requests

def chat(messages, api_key, model="MiniMax-Text-01", timeout=30):
    try:
        resp = requests.post(
            "https://api.minimaxi.com/v1/chat/completions",
            headers={"Authorization": f"Bearer {api_key}"},
            json={"model": model, "messages": messages, "temperature": 0.8},
            timeout=timeout
        )
        resp.raise_for_status()
        return resp.json()["choices"][0]["message"]["content"]
    except requests.exceptions.RequestException as e:
        print(f"API request failed: {e}")
        return None
    except (KeyError, IndexError):
        print("Unexpected API response format")
        return None
```

注意：
- 域名是 `api.minimaxi.com`（不是旧的 `api.minimax.chat`）
- 聊天接口是 OpenAI 兼容格式 `/v1/chat/completions`
- 音乐接口是 `/v1/music_generation`，返回 hex 编码音频

### 大观园树洞

起因是一个学生的毕业设计——做一个红楼梦主题的心理疗愈产品。六个红楼梦角色做AI对话，加上匿名树洞、疗愈音乐、MBTI测试、星座星盘。

前前后后修了十二个bug。两轮代码审查，逐文件逐行。

最后跑通了。十八个文件，两千两百行代码，七个页面全部可用。

部署在Streamlit Cloud上，免费。零成本。

一个人，两周，从想法到上线。

### 代码乡愁

代码最后一行，我写了一个注释：

C THIS IS UGLY BUT IT WORKS

我盯着这行注释看了很久。二十年了，这段代码早就跑不起来了，编译器都换了好几代。但这个注释还在。

因为注释的意义，只有写注释的人自己知道。

这就是《代码乡愁》的起点。一个老程序员，一段三十年前的注释，一个AI试图理解但永远无法完全理解的情感。
